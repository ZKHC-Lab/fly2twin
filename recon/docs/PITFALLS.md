# 3DGS 展示与复现避坑

2026-10-27 · 面向导出程序和查看器维护者

默认展示完整 SH 的 Gaussian PLY，使用采集相机的真实投影，并把自由视角限制在训练采集走廊内。导出契约版本为2；仓库的查看器（[viewer/](../../viewer/README.md)）已接入 scene.json、真实内参与采集走廊，真实产物加载的验收状态见[等价报告](EQUIVALENCE.md)。

## 1. SPLAT 颜色发软，不等于训练模型发软

- **现象：** 相同模型导出成轻量SPLAT后，细节、反光和视角变化显著发软。
- **原因：** 32字节SPLAT只有SH直流项（DC）颜色，丢失非零阶球谐系数和视角相关颜色。加大文件显示分辨率不会恢复这些信息。
- **规避方法：** 首选完整SH的Gaussian PLY，按模型真实SH阶数渲染；SPLAT只作轻量预览，必须标注“仅 DC 颜色的轻量预览，视角相关颜色丢失，细节明显发软”。
- **代码保证：** [export_scene](../io/export.py)总是写完整SH PLY和SPLAT；从系数数量推导并核对SH阶数。scene的`preferred_model`指向完整PLY，`preview_model`明确标注信息丢失。[require_full_sh_model](../io/presentation.py)发现仅SPLAT时警告，并拒绝把它当作完整导出。没有“默认只导出SPLAT”的开关。

## 2. 查看器视场必须来自采集内参

- **现象：** 已验证清晰的办公室模型，在查看器里画面更宽、物体变小、细节发糊。
- **原因：** 展示曾误用58°垂直视场，而采集相机实际约43.3°。这不是同一个投影，不能把查看器默认值当作相机标定。
- **规避方法：** 使用对应帧的K、分辨率、水平/垂直FOV；不是把所有相机硬编码为43.3°。居中主点时 `FOV_y = 2 atan(height/(2 fy))`，水平同理；偏心主点必须用K建立非对称视锥，不能只设置一个对称FOV。等比例缩放K并保留半像素约定；窗口比例不同时使用留边，不拉伸或暗中裁切。
- **代码保证：** [camera_records / field_of_view / viewer_intrinsics](../io/presentation.py)按每帧原生K和分辨率计算并导出两轴视场。计算边界为像素中心约定的`[-0.5, size-0.5]`；查看器辅助函数拒绝58°一类不匹配参数，返回校准后的K。导出的相机NPZ同时保存原图分辨率。外部查看器必须使用该契约/辅助函数，而不是继续用自身默认视场。

## 3. 离开采集走廊会糊，不要抬高视角美化画面

- **现象：** 沿原轨迹清晰，横向挪开、抬高镜头或转向未采集的一侧后出现洞、重影、漂浮片和糊墙。
- **原因：** 3DGS拟合的是已有视角覆盖，缺失方向的表面和颜色没有被充分约束。扩大FOV或抬高视角不能补回未观测信息。
- **规避方法：** 默认从训练相机附近观看；相对同一训练相机，建议平移≤0.15 m、完整旋转差≤15°。非公制SfM场景用0.15个导出场景单位，不能冒称0.15 m；归一化坐标阈值是`0.15 / meters_per_unit`。这是保守导航建议，不是清晰度保证；改善覆盖应补拍，而不是移动展示镜头制造更好构图。
- **代码保证：** [capture_corridor / within_capture_corridor](../io/presentation.py)导出所有采集相机中心、c2w旋转、光轴、训练帧ID、尺度单位和推荐约束。判据要求位置与姿态同时靠近**同一台训练相机**，不把留出相机算作训练覆盖，也不会把来自两台不同相机的最小距离/最小角度拼成合格视角。scene的`viewer_requirements.navigation`要求消费者执行该约束。

## 4. 坐标转换必须同时作用于位置和高斯姿态

- **现象：** 点的位置看起来换到了正确方向，但高斯椭球方向错误，墙面拉丝、变厚或颜色随视角异常。
- **原因：** 只旋转xyz，遗漏高斯四元数或相机姿态；混用xyzw/wxyz；用单轴取反制造反射；或者旋转了世界坐标却仍在错误基底查询SH。
- **规避方法：** 导出世界约定为右手Z-up，高斯四元数为wxyz，相机局部轴仍是CV右/下/前。改变世界基底时，均值、Gaussian旋转、相机c2w全部一起变换；椭球协方差满足`Σ' = R Σ Rᵀ`。显示层变换后，SH查询方向需逆旋回源世界；若把旋转烘焙到独立PLY，还必须旋转各阶SH系数，不能只改xyz和四元数。Z-up是输入/显示约定，不声称纯SfM已估计重力。
- **代码保证：** [transform_scene_coordinates](../io/presentation.py)一次返回共同刚体变换后的点、wxyz四元数和c2w，拒绝反射/非刚体变换；CPU测试验证非平凡坐标往返、相机局部坐标及协方差不变性。[export_scene](../io/export.py)显式标注Z-up/wxyz/SH基底；如果manifest明确声明非Z-up，会拒绝伪装成Z-up输出，要求先对齐整场景，不能默默旋转SH模型。未声明时按Z-up输入约定处理，不能据此推断重力已标定。

## 5. gsplat 1.5.3 的 opacity reset 优先级错误

- **现象：** 前3000步接近基线，但reset后高斯数不下降，最终数量和质量偏离；仅对比版本字符串找不到原因。
- **原因：** 此次核查的公开1.5.3使用 `step % reset_every == 0 & step > 0`；它是包含`0 & step`的链式比较，条件永远不成立。原实验checkout使用正确的`and`。公开1.5.2还存在第0步reset的不同语义。
- **规避方法：** 一行修法：`if step % self.reset_every == 0 and step > 0:`。**待向上游提 PR**。无人机预设保持第0步不reset、后续正整数倍reset；手机预设显式设置 `reset_at_zero: true` 复现1.5.2。两者均在refine_stop_iter停止，不通过改密化阈值凑高斯数。
- **代码保证：** [BaselineStrategy](../gaussian/strategy.py)显式编排状态累计→grow→prune→清累计→reset，不调用有错的发布版callback。已有CPU测试覆盖0/3000/6000/15000步与真实opacity/optimizer参数替换；训练已按该实现通过原复现门槛。改编代码的Apache许可与版权保留在[许可文件](../../licenses/gsplat-APACHE-2.0.txt)。

## 6. 固定归一化和重新计算不能混为同一对照

- **现象：** 输入和参数看似一样，训练尺度、相机学习率相关量、初始高斯尺度及最终点数却改变。
- **原因：** 比较旧实验时重新计算center/meters_per_unit/scene_scale，或换场景后仍盲目复用旧数值。
- **规避方法：** 精确复现早期办公室无人机参考训练时，固定那次参考配置的三项归一化：center=`[-7.171480196455258, 8.188519718807234, 0.9049076656900958]`，meters_per_unit=`8.941428986458085`，scene_scale=`1.1180742025375368`，容差atol=1e-7、rtol=0。新场景默认重新计算，不能套用办公室数值。两种口径都在配置和报告中说明；稀疏场景错位相机还可能要求单独的稳健归一化评估。
- **代码保证：** [normalization](../geometry/transforms.py)通过显式fixed参数区分两种路径；[管线加载器](../pipeline.py)支持normalization/normalization_file。CPU测试分别验证固定和新场景重新计算；没有自动把本机旧实验配置当全局默认。

## 7. 白墙增量 SfM 断裂：换全局式，不拿局部注册冒充整场景

- **现象：** 室内白墙、玻璃和重复工位导致序列断成多个模型，最大模型只覆盖少部分图像。
- **原因：** 增量注册在弱纹理/弱基线处难以持续连接，后续训练不能补回缺失位姿。
- **规避方法：** 尝试GLOMAP全局式求解并检查注册率、子模型和异常位姿；必须保留相同输入/匹配条件的比较。手机管线同一1200帧密帧序列，原报告注册率记为37.6%→92.7%；对应增量式最大模型451帧、全局式1113帧（1113/1200精确为92.75%）。注意正式导出后有效位姿是1105/1200=92.1%，不要把求解注册数和最终导出数混写；该数据结论不是所有白墙场景的保证。
- **代码保证：** [SfM编排](../poses/pipeline.py)报告输入数、最大模型注册率和所有子模型；拒绝静默丢弃帧，并在部分注册时输出GLOMAP建议。[GLOMAP 实现](../video/sfm.py)的序列匹配加回环与去畸变现已接入 `pose.provider: glomap`，`colmap` 保留增量式入口；两者在分阶段流程都拒绝部分注册。[等价报告](EQUIVALENCE.md)里从视频端到端复现的结果是历史 RGB-only 质量，不当作当前手机预设的 GPU 验收，也不将外部手机管线的92.7%当成本包成绩。

## 8. 落地 BA 的位姿每次运行不同，对比下游做法时要共用同一份位姿

- **现象：** 同样的输入和代码，`pose.refine: ba` 跑两次，相机位姿不同。office_gs_01（494 帧）实测：位置差中位 1.3 cm、九成位 4.5 cm、最大 41 cm，43 帧超过 5 cm；两次运行各自融合的点云到雷达地图的 P50 / P90 为 4.34 / 13.18 cm 和 4.22 / 11.90 cm。深度阶段的深度和置信度逐位相同，融合阶段在同样的上游输入下逐字节相同。
- **原因：** 两次运行的 SIFT 验证后匹配数就不同（854,545 对 855,529），差异从特征匹配开始，BA 收敛到不同的解。匹配数为什么不同没有查明。
- **规避方法：** 运行目录按配置指纹区分，改任何一个键都会从头重跑，位姿随之改变。要隔离下游改动（融合、训练）的效果，在同一个运行目录的位姿上比较：融合阶段可以用 `recon.pipeline.fuse(cfg, out, root)` 在已有运行目录上重做，[回访约束](../../recon_core/README.md)的离线对照就是这样做的。单次运行的距离数字带着这份波动，报告时写明来自哪一次运行。
- **代码保证：** 没有。流程不固定这一步的结果，也不检测两次运行之间的差异。
