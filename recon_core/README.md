# recon_core

机载端（ROS，Python 3.8）和离线端（Python 3.10）共用的数值核心，只依赖 NumPy / SciPy；读 RGB 时才导入 OpenCV。
约定：位姿是相机到世界的 4×4 矩阵（OpenCV 光轴：右、下、前），世界系为米制、Z 轴向上，深度是沿光轴的米制 z。

| 模块 | 内容 |
| --- | --- |
| `scale.py` | 窗口尺度：轨迹先验 + 相邻窗口共享帧深度比（可选再加跨窗口重叠帧深度比 `cross_view_log_ratio`），对数域加权最小二乘；`batch_window_scales` 处理一整段已完成的窗口 |
| `fusion.py` | 单帧置信度/深度边缘掩码、近邻视角选取、多视一致性融合、体素降采样 |
| `revisit.py` | 回访约束：融合之前，用别的窗口也看到的表面给每帧再解一个深度尺度修正量；只改尺度，不改位姿 |
| `ply.py` | 二进制 PLY 写出 |

## 参数

| 项 | 值 |
| --- | --- |
| 轨迹先验 | 提供者轨迹范围 > 0.3 m 才使用，权重 min(范围, 2) |
| 相邻边 | 至少 3 个共享帧（批处理）；每帧取两窗置信度都**高于**本帧中位数、深度为正的像素，像素数 ≥ 500；权重 3 |
| 跨窗口行（可选） | 两帧属于不同窗口：帧 i 的米制深度按位姿投到帧 j，与帧 j 深度比较；目标深度在 0.3–4 m、\|log 比\| < 0.25 的像素计入，像素数（换算到模型分辨率）> 500；取中位数。每个有方向的帧对一行，权重由调用方给（机载 `g4_cross_window_weight` 开启时用 0.3；当前机载主线改用下一行的逐帧尺度，两者二选一） |
| 逐帧尺度（可选，`solve_frame_scales`） | log s_f = x_w + d_f；轨迹先验 σ 0.04、相邻边 σ 0.04、帧对行 σ 0.08、帧偏离 σ 0.04、窗内相邻帧偏离变化 σ 0.02，权重 1/σ，scipy lsqr；没有先验锚定的连通块不求解 |
| 回访约束（可选，`revisit.frame_log_scale_corrections`） | 成员点：融合的隔点像素网格上每隔一列取一列，通过多视一致性检查的点（`fusion.supported_points`，与 `frame_points` 对这些像素的判定相同），带朝向相机的深度图法线。每个窗口取至多 3 万个点，与其他窗口落在其包围盒外扩 0.3 m 内的点（至多 50 万个）做最近邻匹配，两法线夹角余弦 > 0.6；门限 20 → 12 → 8 cm 共三轮。残差是点到面距离，Huber 阈值 3 cm，单次匹配 σ 3 cm、相关性折算系数 30；每帧修正量先验 σ 0.03，窗口内相邻帧之差 σ 0.01；每轮每帧改变量不超过 0.05。SciPy 稀疏直接求解，不用随机数 |
| 单帧掩码 | 置信度高于中位数，深度 > 0，3×3 邻域深度相对极差 ≤ 0.03 |
| 近邻视角 | 1.5 m 内、夹角 < 30°，按 夹角/30 + \|距离 − 0.3 m\| 取前 6 个 |
| 一致性 | \|log 深度比\| < 0.03 计为支持；支持数 ≥ min(2, 可见视角数)；0.3 m < 深度 < 4 m；步长 2 |
| 体素 | 2 cm 起；点数超过上限时按 max(1.1, (点数/上限)^(1/3)) 放大，从 2 cm 点云重新降采样 |

## 来源与等价性

由三份实现合并而来：离线包 `dronerecon` 的 fusion/scale、G4 逐帧位姿放置 `g4_backend/frame_pose.py`、`drone3d_onboard/fusion.py`。合并时统一了一处差异：G4 在线版计算共享帧深度比时取置信度 ≥ 中位数的像素，现与离线版一致取 > 中位数；真实 VGGT 置信度没有重复值，每帧最多相差一个像素。体素降采样用 NumPy 实现，网格原点与 Open3D 相同（min − 体素/2），输出按体素字典序排列；三维体素编号合成一个 int64 键后排序、用 bincount 累加（每轴编号 < 2^21，超出时退回逐行 unique），与逐行 unique + add.at 的旧实现逐位相同（`tests/test_fusion.py`）。

融合按帧拆成 `frame_points`（单帧多视一致性检查后的点）、`frame_image` / `frame_colors`（颜色）和 `cloud_from_frames`（2 cm 体素与自适应放大）；`colored_cloud` 依次调用它们。机载在线点云用这些函数做按帧增量（`drone3d_onboard.session.SessionFusion`）。

已验证（2026-10-29，E1 无人机 V1.0 输入：670 帧、23 个窗口、512×288）：

| 项目 | 结果 |
| --- | --- |
| 窗口尺度、逐帧尺度、轨迹拟合、相邻边 | 与 dronerecon 逐位相同 |
| 深度缓存、单帧掩码 | 逐位相同 |
| 融合点云 | 2 cm 点数 2,732,886、最终 848,586 点、体素 0.03383419681295737 m；按坐标排序后 XYZ / RGB（float32）逐位相同 |
| CPU 融合耗时 | 136 s（4 线程）；2026-11-03 体素降采样改为整数键后 78 s，点数、体素与按坐标排序后的 XYZ / RGB 仍与上表逐位相同 |

## 回访约束

**解决的问题**：尺度求解只在位姿相近的视角之间建立深度约束（融合的近邻视角：1.5 m、30° 以内）。同一处表面被另一个窗口从别处看到时（相邻窗口，或隔一段时间飞回来），两个窗口的尺度互不约束，各自偏差几个百分点，融合后同一面墙出现两层。

**做法**：尺度解完之后、融合之前执行。取融合会保留的点，按拥有该帧的窗口分组；每个窗口的点与其他窗口的点做点到面匹配；把所有帧的对数尺度修正量放进一个稀疏最小二乘里一起解，修正量被拉向零，并在窗口内保持平滑。帧 f 的米制深度乘以 exp(修正量)。

**接入位置**：离线流程的融合阶段由配置 `fusion.revisit` 开启（缺省关闭，输出与此前逐位相同）；机载交付包导出默认开启，`--no-revisit` 关闭；在线点云（`SessionFusion`）不做这一步。

**验证**（2026-11-19；五次真实采集、两个场景，都是机载 1× 回放的交付包；参照是同一次录制的雷达图，不配准；距离口径同 [雷达评测](../recon/docs/LIDAR_EVAL.md)，另报 2 cm 点云的 5 cm 内比例和完整度；完整度 = 离点云 1 m 以内的雷达点中，5 / 10 cm 内有融合点的比例）：

| 采集 | 帧数 / 窗口数 | 交付体素下 P50 / P90：原 → 开启 | 2 cm 点云 5 cm 内 | 完整度 5 cm / 10 cm | 本步用时 |
| --- | --- | --- | --- | --- | --- |
| office_gs_01（办公室，155 s） | 494 / 14 | 3.69 / 9.17 → 3.30 / 7.32 cm | 69.3% → 78.1% | 32.6 / 45.6% → 35.1 / 47.3% | 10 s |
| office_gs_02（办公室，234 s） | 529 / 15 | 3.30 / 7.99 → 3.06 / 6.79 cm | 78.3% → 84.0% | 36.6 / 49.3% → 37.0 / 49.6% | 12 s |
| office_gs_03（办公室，550 s） | 1685 / 48 | 3.49 / 11.30 → 3.25 / 8.98 cm | 71.3% → 77.6% | 31.0 / 44.3% → 30.8 / 44.1% | 57 s |
| ctrl_wall_01（休息区，236 s） | 495 / 14 | 3.20 / 10.40 → 2.98 / 7.43 cm | 73.9% → 81.1% | 48.3 / 56.4% → 48.8 / 56.5% | 16 s |
| office_gs_04（办公室，27 min） | 3470 / 116 | 3.30 / 11.17 → 3.03 / 7.36 cm | 79.0% → 86.6% | 48.9 / 60.3% → 48.9 / 60.7% | 247 s |
| office_gs_04，落地 BA 位姿、离线分窗、512×288 | 2935 / 116 | 2.92 / 6.74 → 2.74 / 4.64 cm | 87.7% → 93.9% | 48.8 / 62.0% → 47.1 / 61.4% | 347 s |

- 五次采集的 P90 都下降 15–34%，5 cm 内的比例提高 6–9 个百分点；完整度变化在 ±0.5 个百分点以内（01 提高约 2 个百分点）。落地 BA 那一行的 5 cm 完整度降 1.6 个百分点：重复的表面层合并后，表面变薄。
- office_gs_04 的两行“原”值与该场景已公开的数字一致（机载 3.3 / 11.2 cm，落地 BA 后 2.9 / 6.8 cm）。叠加在 BA 位姿之上仍然有效：BA 修位姿，这一步修每帧的尺度。
- 各帧修正量的绝对值中位数 0.6–1.4%，最大 5–12%。
- 用时是台式机（6 线程，空闲）测的。office_gs_03 的 57 s 里，取成员点约 14 s，匹配和求解约 44 s（每个窗口每轮要对其他窗口的点建一次最近邻树）。NX 上未测。
- 产品路径复核：office_gs_04 的机载记录用 `drone3d_onboard.export` 重新导出，`cloud.ply` 为 864,610 点、体素 4.59 cm，用 `recon lidar-distance` 评测为 P50 3.02 / P90 7.32 cm、5 cm 内 81.1%（原交付 880,636 点、4.86 cm、3.32 / 11.17 cm、71.5%）。同一台机器同样状态下，整个导出不开这一步 581 s，开启 863 s；不开时的 `cloud.ply` 与原交付逐字节相同。离线一侧，office_gs_04 落地 BA 的运行目录用 `recon.pipeline.fuse` 加 `fusion.revisit: true` 重做融合阶段，`initial.npz` 为 839,215 点、体素 4.09 cm，评测为 P50 2.73 / P90 4.65 cm、5 cm 内 91.4%（原结果 850,318 点、2.92 / 6.77 cm、84.1%）；融合阶段共 702 s，其中这一步 347 s。

**边界**（已知，未解决）：

- 只改尺度。两趟之间的位姿误差也会被当作尺度吸收。
- 两处表面之间的间隙由两端的帧共同承担，离表面远的一帧承担得更多（各帧先验相同时，它需要的尺度改变量更小）。单元测试里：近处的窗口偏深 4%、远处的窗口正确，结果是远处的窗口 +1.3%、近处的 −0.5%，两面墙重合，但正确的窗口被改动了。真实数据上总体误差下降。有逐帧真值的合成数据上（渲染房间加真实 VGGT，不含玻璃的房间，各房间的中位数），逐帧绝对尺度误差在 384×224 下从 2.8% 降到 2.1%（169 间里 160 间下降），512×288 下从 1.8% 降到 1.3%（101 间里 90 间下降），超过 5% 的帧从 23% 降到 15%、从 8.7% 降到 5.4%。
- 匹配要求两个法线同向（都朝向各自的相机），所以薄墙的正反两面不会互相匹配。厚度小于门限、且两面被同侧斜着看到的结构仍可能误配。
- 与别的窗口没有共同表面的帧保持原尺度；相邻窗口通常有共同表面，所以单程采集也会被调整。
- 所有窗口一致的尺度偏差，这一步看不到。
- 两个强度参数（先验 σ、平滑 σ）各放宽到 4 倍，在 99 个合成房间上 5 cm 内的比例只变化 1.4 个百分点；没有对着雷达评分调过参数。

## 测试

```bash
python -m pytest recon_core/tests            # 离线环境
python3 -m unittest discover -s recon_core/tests -t .   # ROS 环境
```
